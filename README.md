# Отклик

Готовый MVP сервиса форм для карьерного центра. Менеджер собирает форму без разработчика, публикует ссылку и читает отклики студентов. Интерфейс на русском, работает на компьютере и телефоне.

## Запуск

Нужен **Node.js 20 или новее** с npm. В корне репозитория выполните ровно две команды:

```sh
npm install
npm start
```

Откройте **http://localhost:3000/admin**. Авторизации нет. Хранилище создаётся автоматически при первом запуске; сборка, ключи и СУБД не нужны. Приложение не обращается к внешним API, шрифтам или CDN. Сторонних npm-зависимостей нет.

Другой порт (после установки):

```sh
# macOS / Linux
PORT=3100 npm start
```

```powershell
# Windows PowerShell
$env:PORT = '3100'
npm start
```

При изменении порта используйте http://localhost:3100/admin. Ссылка на форму строится из адреса, по которому открыта админка. Остановка — Ctrl+C. Если порт занят, сервер завершится с понятной ошибкой.

## Как проверить основной сценарий

1. Откройте `/admin`, нажмите «Создать форму». В пустом пространстве также есть шаблон стажировки с четырьмя вопросами.
2. Введите название и описание. Добавьте короткий текст, длинный текст, email или один вариант ответа. Включите «Обязательный» для нужных вопросов.
3. Названия, типы и варианты редактируются на месте; стрелки меняют порядок; корзина удаляет вопрос после подтверждения. Справа на широком экране — предпросмотр.
4. Нажмите «Сохранить» для черновика либо «Опубликовать» — публикация сначала сохраняет текущие изменения. Скопируйте уникальную ссылку `/f/<uuid>`.
5. Откройте её в другой вкладке как студент, заполните и отправьте форму. Пустые обязательные ответы и неверный email будут отмечены. После успешной записи появится подтверждение.
6. Вернитесь в конструктор → «Отклики». Нажмите «Обновить», если вкладка была открыта заранее. Раскройте карточку: внутри все ответы и номер версии.
7. Перезапустите приложение: формы, ссылки, версии и отклики останутся на месте.

Для проверки сбоя отправки заполните публичную форму, остановите сервер и нажмите «Отправить отклик». После сообщения об ошибке ответы останутся на странице. Запустите сервер и повторите отправку. При доступном `sessionStorage` ответы также восстановятся после перезагрузки этой вкладки.

## Границы MVP и принятые решения

- Ручное сохранение черновика менеджера. Выход с несохранёнными изменениями требует подтверждения; при закрытии вкладки браузер предупреждает. Автосохранения администратора нет.
- Сохранение и публикация — два отдельных запроса. Если черновик уже сохранён, но ответ на публикацию не получен, интерфейс показывает сохранённый черновик и сообщает, что публикацию не удалось подтвердить. При потере HTTP-ответа сервер мог выполнить запрос: обновите страницу, чтобы проверить версию. На время сохранения или отправки переходы внутри приложения блокируются.
- У формы один редактируемый черновик и неизменяемые опубликованные версии. «Сохранить» не меняет публичную форму. Публикация изменённого черновика создаёт следующую версию по **той же ссылке**. Публикация без изменений не создаёт лишней версии.
- Каждый вопрос имеет постоянный UUID. В отклике сохраняются снимок вопросов, заголовок формы, порядок, варианты и ответы по UUID. Переименование, смена типа, перестановка или удаление вопроса не искажают старые отклики.
- Уже открытая студентом версия принимается и после новой публикации. Это позволяет закончить заполнение без потери данных. Старая версия явно указана в отклике. Новые посетители получают последнюю публикацию.
- Уточнение правил конструктора не запускает повторную валидацию исторических снимков при чтении. Например, вариант с переносом строки, допустимый в прежней версии сервиса, остаётся доступным в той публикации; при сохранении нового черновика варианты уже должны соответствовать текущим правилам.
- Черновик студента привязан к форме и версии в `sessionStorage`: живёт в пределах вкладки, не переносится в другую вкладку/браузер и обычно удаляется при закрытии вкладки. При новой версии начинается отдельный черновик; смешивать ответы разных схем нельзя. При недоступном хранилище форма работает в памяти до перезагрузки.
- Каждая попытка имеет UUID `requestId`. Повтор с той же версией и теми же нормализованными ответами после сетевой ошибки, двойного клика или потери HTTP-ответа возвращает прежний результат и не создаёт дубль. Если под уже сохранённым `requestId` пришли другие ответы или версия, сервер возвращает 409: старый отклик не меняется, новый не создаётся, интерфейс сохраняет введённые изменения и не показывает ложный успех. Для того же `requestId` валидация также обязательна: неверный ответ даёт 422. Это защита от повтора запроса, а не запрет человеку откликаться из других браузеров. Страница подтверждения сохраняется на время сессии вкладки.
- У менеджера есть `revision`: устаревшая вкладка получает 409 вместо молчаливой перезаписи чужих изменений. Её текст остаётся на странице; перед обновлением его можно скопировать.
- Ограничения и валидация общие для браузера и сервера, описаны ниже. При сохранении передаются только название, описание, вопросы и ревизия; опубликованные снимки и статистика обратно не отправляются.
- Отложены авторизация, файлы, условные вопросы, экспорт, уведомления и продвинутая аналитика: основной сценарий важнее.

### Единые правила ввода

Источник правил — `public/validation.js`: его импортируют сервер и браузер. Конструктор проверяет данные до сохранения/публикации, публичная форма — до отправки, сервер повторяет ту же проверку независимо от клиента. Значения `maxlength` и ограничение числа вопросов также берутся из этого модуля.

| Данные | Максимум |
| --- | --- |
| Вопросы в форме | 30 |
| Название / описание формы | 160 / 2000 |
| Текст вопроса | 240 |
| Варианты одного вопроса | 20; для публикации минимум 2 |
| Текст одного варианта | 160 |
| Короткий ответ / email | 500 / 254 |
| Длинный ответ | 5000 |

Все текстовые ограничения измеряются в **единицах UTF-16**, как `maxlength` в браузере и `String.length` в JavaScript: например, большинство emoji занимают две единицы. Длина проверяется до удаления пробелов по краям; после проверки эти пробелы удаляются. Пустой необязательный ответ сохраняется пустой строкой, непустой email проверяется даже в необязательном вопросе. Проверка email упрощённая: `name@domain.tld`, без проверки существования адреса или DNS.

Название формы, текст вопроса, варианты, короткий ответ и email однострочные: API отклоняет CR/LF, которые нельзя ввести в соответствующее однострочное поле интерфейса. В описании и длинном ответе разрешены переносы. Ответы должны быть строками; `null`, числа и массивы не принимаются.

В редакторе вариантов каждый вариант вводится с новой строки. Пустые строки, включая последнюю, игнорируются до подсчёта; дубликаты проверяются после удаления пробелов, с учётом регистра. Общего ограничения длины редактора нет: вместо обрезания всего списка проверяются число вариантов и длина каждого. Предпросмотр также исключает пустые строки. Черновик может содержать вопрос без названия и менее двух вариантов; публикация требует заполнить вопрос и добавить минимум два варианта. Превышение лимитов и дубликаты блокируются и при сохранении черновика.

Тело JSON-запроса ограничено **1 МиБ в байтах**: этого хватает на 30 длинных ответов по 5000 единиц даже при JSON-экранировании (до 900 000 байт плюс ключи и метаданные), а также на максимальную схему формы. Превышение размера запроса даёт 413, ошибка отдельного поля — 422. Запрос, отклонённый валидацией, не изменяет данные; введённые данные остаются в интерфейсе для исправления. Сетевая ошибка сама по себе не доказывает, что сервер не успел сохранить данные.

## Аналитика незавершённых откликов

Во вкладке «Отклики» показаны три счётчика за всё время по всем версиям формы:

| Показатель | Подсчёт |
| --- | --- |
| Открытия | Уникальная пара `formId + sessionId` после загрузки публичной формы и доставки события `open`. |
| Начали заполнять | Та же пара после первого изменения ответа; проверка поля на валидность не требуется. Восстановленный непустой черновик также считается начатым. |
| Успешно отправили | Число сохранённых откликов, с дедупликацией по `formId + requestId`. |

`sessionId` хранится в `sessionStorage` для формы. Перезагрузка той же вкладки не увеличивает открытия и начала. Успешная отправка дополнительно гарантирует наличие открытия и начала, даже если предыдущие события не дошли. Ответы и события пишутся независимо; сбой аналитики не блокирует отправку.

**Ограничения:** это сессии, не уникальные люди. Новая независимая вкладка/браузер создаёт новую сессию; дублированные браузером вкладки иногда наследуют `sessionStorage`. Без `sessionStorage` перезагрузка создаёт новую сессию. Блокировщики, потеря сети и закрытие вкладки до доставки события занижают показатели; боты могут их завышать. Из-за разных единиц учёта и прямых запросов к API это ориентировочная воронка, а не точная конверсия. Периодов, когорт и аналитики по вопросам нет.

## Архитектура и хранение

```text
server.js            HTTP-сервер, REST API, валидация, транзакции JSON
public/index.html    Оболочка приложения
public/app.js        Интерфейс менеджера и студента, клиентская валидация
public/validation.js Общие лимиты, нормализация, проверка формы и ответов
public/styles.css    Адаптивные стили без внешних ресурсов
data/store.json      Автоматически создаваемые данные, исключены из Git
test/api.test.js     Интеграционные тесты с отдельным временным хранилищем
test/client.test.js  Проверки реального кода UI с минимальными DOM-заглушками
docs/                История AI и результаты проверки
```

Node.js `http` раздаёт приложение и API с одного origin. Клиент использует History API. Данные целиком загружаются в память одного процесса. Каждое изменение выполняется последовательно: копия состояния → временный файл → `fsync` → атомарное переименование → замена состояния в памяти. Успешный ответ отправляется только после записи. Ошибка записи не применяется к памяти. Повреждённый JSON останавливает запуск и не перезаписывается пустым файлом.

JSON выбран ради запуска без зависимостей и понятной проверки тестового задания. Один процесс, одна локальная файловая система, небольшое число форм и откликов. **Нельзя запускать несколько экземпляров с одним файлом:** межпроцессной блокировки нет. Каждая запись переписывает весь файл; для нагрузки нужен SQLite и затем отдельная БД. Защита от отключения питания зависит также от ОС и диска, резервного копирования нет. Для бэкапа остановите приложение и скопируйте `data/store.json`.

Необязательная переменная `DATA_FILE` задаёт отдельный файл для изолированных проверок. По умолчанию путь всегда относительно корня проекта, независимо от текущей директории процесса. Пользовательские данные не попадают в GitHub. Свежая установка начинает с пустого списка.

### API

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/admin/forms` | Список форм и счётчики |
| `POST /api/admin/forms` | Новый черновик |
| `GET /api/admin/forms/:id` | Черновик, последняя публикация и статистика |
| `PUT /api/admin/forms/:id` | Сохранить с текущей `revision` |
| `POST /api/admin/forms/:id/publish` | Опубликовать с текущей `revision` |
| `GET /api/admin/forms/:id/responses` | Отклики со снимками вопросов |
| `GET /api/forms/:id` | Только последняя публичная версия |
| `POST /api/forms/:id/events` | `open` или `start` с `sessionId`, `version` |
| `POST /api/forms/:id/responses` | `answers`, `version`, `sessionId`, `requestId` |

## Проверки

```sh
npm test
```

Тесты используют встроенные `node:test`/`assert`, поднимают реальные HTTP-процессы с временными файлами, проверяют публикацию, четыре типа полей, граничные значения, согласованность клиентских и серверных ошибок, максимальную форму, повтор отправки и конфликт изменённого запроса, совместимость старых снимков, конкурентные изменения, `PORT`, перезапуск и повреждённое хранилище. Дополнительно код UI исполняется в Node `vm` с минимальными DOM-заглушками для проверки HTML-лимитов, клиентского отказа до запроса, состава сохраняемого черновика, частичного сбоя публикации, навигации во время отправки и позднего ответа при смене вкладки. Эти тесты не заменяют реальный браузер; браузерные проверки записаны отдельно. Рабочие данные не затрагиваются.

Результаты реально выполненных проверок, включая чистую установку и браузерный сценарий, — в [docs/VERIFICATION.md](docs/VERIFICATION.md). Использование AI и история работы — [AI_USAGE.md](AI_USAGE.md), [docs/AI_SESSION.md](docs/AI_SESSION.md).

## Ограничения развёртывания и следующие шаги

Админка и её API **намеренно открыты без авторизации по условию задания**. Любой, кто имеет сетевой доступ к серверу, может читать отклики и менять формы; UUID не заменяет разграничение доступа. Это локальный прототип, его нельзя выставлять в интернет с реальными персональными данными. Есть экранирование пользовательского текста, CSP и проверка Origin браузерных записей; это не заменяет авторизацию. Для удалённого использования нужны HTTPS, права доступа и политика обработки данных.

Разумное продолжение: авторизация менеджеров → SQLite с миграциями и резервными копиями → пагинация и экспорт откликов → автосохранение черновиков менеджера → измерение отвалов с согласованной моделью сессий. Без добавления этих задач основной сценарий уже завершён.
